# Methodology

费米子乐园把上下文治理分成两个层次：任务 Agent 决定“谁负责什么”，`ctx-key` 只决定“下一步给他哪些材料”。确定性评分、预算压力和可恢复账是 Skill 内部机制，不冒充多个 Agent。

## v0.1 机制

1. `record` 把新证据放入在位区并写账。
2. `select` 根据任务态与目标角色生成判据，使用零网络 BM25 风格词面基线排序。
3. `compact` 在预算压力下保留强制项与高分项，把其余项移入可恢复区。
4. `recall` 在任务变化或验证失败后，用新触发从可恢复区召回相关项。
5. 每条决定记录动作、分数、理由、上下文版本与 `trace_id`。

## 与私人实验的关系

- 早期流式实验实际运行过“位置有限、判出局、任务判据变化、被移出项重新竞争”的机制。
- 第 120 轮实际比较最近历史、全量或压缩历史、动态产判据后选读历史三种方式，并用隐藏测试机械判卷。
- 本仓库的 Python API 是从这些机制整理出的新公开边界；它不是第 120 轮脚本的逐行改名，也没有继承其闭源模型依赖。

## 验收纪律

上下文体积只是过程指标。最终应以隐藏任务成功率、重复失败率、错误移出率和召回恢复率判断价值。任何收益主张都必须事前冻结门槛，并与全量、摘要和简单位置基线比较。
