# JDDC-185 · 对照臂上下文增长：那个「322 条 / 70,784 token」的可核账

这一格只支撑一句话，别的什么都不主张：

> **在 322 条真实客服流上，默认 compaction 策略一次都没触发，单 turn 请求量单调涨到 70,784 token。**

它在别处被当**对照**引用（例如 [`../s0-shop-shift/`](../s0-shop-shift/) 里说明「52 点的 S0 班太短、
压缩三臂 0 次触发、长班糊化没测到」）。原先那句引用只有数字、没有账，第三方核不了；本目录补上账。

## ⛔ 先说边界

- **料不在这儿，也不会在这儿。** 这次跑的输入取自 **JDDC（京东客服对话数据集）**，受其许可约束，
  本仓不再发布对话内容；跑出来的 session 账里含逐字对话，同样不发布。
- ⟹ **本目录发布的是「数」，不是「料」**：逐 turn 的 token 计数、事件计数、料形描述，
  外加输入文件的 sha256 —— 够核「这些数是从哪个文件、按什么口径数出来的」，
  **⛔ 不够让一个没有 JDDC 授权的人重跑出这次运行**。
- **这不是本仓引擎的读数**：对照臂跑的是 dsh 自带的默认 compaction 策略，
  `fermion_garden` 的 `select / compact / recall` 没有参与这一臂。本目录不含任何成功率主张。

## 数（`summary.json` 逐字）

| | 读数 |
|---|---|
| 喂入客户消息数 | **322**（16 个会话，逐会话条数见 `料形-边界.json`） |
| assistant turn 数 | 322 |
| **compaction 事件数** | **0** —— 整流从没压缩过 |
| 首 turn 请求量（in＋cacheRead） | 587 |
| **末 turn 请求量（in＋cacheRead）** | **70,867**（其中 cacheRead **70,784**） |
| cacheRead 是否单调不降 | **是** |
| inputTokens 最大值 | 474 |
| 总请求量（in＋cacheRead，322 turn 累计） | 12,082,690 |

⚠️ **口径必须连着读，否则这一栏会被读小两个数量级**：`inputTokens` 只记**缓存未命中**的那部分。
这一臂单看 `inputTokens` 最大才 **474** —— 那不是省，是被 prompt 缓存盖住了。
单 turn 的真实请求量是 `inputTokens + cacheReadTokens`。

逐 turn 全量在 [`token-trajectory.csv`](token-trajectory.csv)（322 行，纯数字，无对话内容）。

## 料形（`料形-边界.json`）

16 个会话、322 条消息，每会话条数与首问位置逐个列出；另有两个 sha256：

- `料源sha256` = `da864d86…68c` —— JDDC 原始切片；
- `串流sha256` = `cd917ecf…ade1` —— 由原始切片按「文件序前 M 个（≥10 条且消息全非空）的会话，
  累计 ≥320 停、M≤20」这条规则拼成的串流。

⟹ **持有 JDDC 授权的人可以按这条规则重建串流，比对 `串流sha256` 逐位对上**，
从而确认「这 322 条到底是哪 322 条」。⛔ 这仍然复现不了本次运行的模型回复（采样、模型版本、缓存状态都不冻结）。

## 这个数在什么情况下会失效

- **换模型或换端点**：70,784 是这一具体端点在这一具体流上的读数，不是常数。
- **换 compaction 阈值**：0 次触发的原因是默认阈值按容量算（0.8×128k），
  70.8k 没够着 —— 阈值一改，这一栏立刻不成立。
- **换料**：干扰密度比班长更决定糊化。322 条**都不够**长到触发压缩，
  这正是引用它的那个地方要说的：**想量「长班糊化」，拉班长是没用的。**
